## 1. 리워드 구조 요약 (코드로 확인한 값)

- 매 물리틱(`Fixed Timestep` 0.02s = 50Hz)마다 `FixedUpdate`에서 쉐이핑을 적용한다
  (`blackout/.../ML/BlackOutEpisodeCoordinator.cs:107-112`). 결정은 `decisionPeriod=2`라 초당 25번
  (420초 매치 ≈ 10,500 결정)이고, ML-Agents가 결정 사이 2틱의 리워드를 합산한다.
- **팀 포텐셜 Ψ**: `η·(γ_s·Ψ' − Ψ)`, `Ψ = tanh((확정점수차 + 보유가치차)/40)`. 5명 전원에게 똑같이
  브로드캐스트되는 제로섬 보상이다. 보유가치는 `exp(−hazard·τ)`로 할인되며 hazard는 가장 가까운 적과의
  거리에 반비례한다 (`PotentialRewardCalculator.cs:46-55,109`).
- **개인 네비 포텐셜 Φ_i**: `η_nav·(γ_s·Φ' − Φ)`, `Φ = 1 − tanh(경로거리/12)`. 빈손이면 가장 가까운
  미점유 아이템까지의 거리에 그 아이템에서 저장소까지 거리를 더하고, 들고 있으면 저장소까지 거리를 쓴다
  (`IndividualNavPotentialCalculator.cs`).
- **종료 보상**: 에이전트당 승 +1 / 패 −1 / 무 0.
- `reward_config.json` 값: `potentialEta=0.25`, `potentialGamma=0.99995`, `potentialScale=40`,
  `hazardCoefficient=0.05`, `navPotentialEta=0.08`, `navPotentialScale=12`. 고정 이벤트 보상은 전부 0.
- **학습 쪽**: 팀 리워드 = 유닛 5명 리워드의 합(종료 시 ±5). 흡수(20초)마다 `buffer_done`으로 부트스트랩을
  끊는다. γ는 BBF 리셋(40k 스텝마다)이 올 때마다 0.97 → 0.997로 다시 어닐링된다. Python 쪽에서 벽 충돌
  페널티 `0.02 × 막힌 유닛 수`를 더한다.

## 3. 가설

각 가설에 대해 근거, 예상 증상, 입증 방법을 적었다. 입증 방법의 "새 로그"는 2026-09-15에 추가한
TB 태그를 뜻한다(§7 참고). Run 6부터 기록된다.

### H1. 쉐이핑 γ와 학습기 γ의 불일치로 포텐셜 쉐이핑의 정책 불변성이 깨짐
- **상태: 약화됨** (TB 1차 확인에서 리셋 경계에 맞춘 Q 이동이 안 보임)
- **근거**: Unity 쉐이핑은 결정당 γ_s² ≈ 0.9999인데 학습기 γ는 0.97~0.997이다. 둘이 다르면 쉐이핑이
  `η(γ_L·Ψ' − Ψ)`(정책 불변 부분)과 `η(γ_s² − γ_L)·Ψ'`로 쪼개지고, 뒤쪽이 "앞서 있기만 하면 매 결정 보상"이라는
  **정책 불변이 아닌** 항이 된다. 데이터셋 기준 팀 단위 평균 |추가항|은 γ=0.97일 때 0.0143(종료 제외 평균
  \|r\|의 4.4배), γ=0.997일 때 0.0014(42%). 네비 포텐셜 Φ에도 같은 구조가 있다(Φ∈[0,1]이라 항상 양수 →
  목표 근처에 머물기만 해도 보상).
- **예상 증상**: 지고 있을 때 행동과 무관한 상수 페널티가 붙어 Q가 음수로 끌려감. 리셋마다 지배적 리워드
  성분이 바뀌어 타깃이 비정상적이 됨.
- **1차 확인 결과 (Run 5 TB)**: γ=0.97 구간은 리셋 직후 약 5천 스텝뿐이라 전체의 12% 정도다.
  `td_error/mean`은 리셋 직후 튀지만(0.25 / 0.18 / 0.40, 평상시 0.10~0.14) 인코더 shrink-perturb와
  n_step 10→3 전환이 동시에 일어나 원인을 분리할 수 없다. `q_value/mean`은 리셋과 맞물린 이동이 없다.
- **입증 방법**:
  1. Run 4(`runs/offline/20260914-223935_81173`)와 Run 5의 `q_value/mean` 궤적 비교. Run 4는 γ 구조는
     같고 온폴리시 데이터가 없으므로, Run 4에서도 Q가 꾸준히 떨어졌다면 H1 쪽, 아니면 H8 쪽 (**학습 없이 지금 가능**).
  2. A/B: `potentialGamma`를 학습기 γ_end에 맞춘 값(`0.997^(1/2)` ≈ 0.9985/물리틱)으로 바꾸거나, 학습기에서
     γ를 고정하고 리셋 재어닐링을 끈 짧은 런(4만 스텝)으로 `q_value/mean` 기울기 비교.
- **주의**: 리워드는 데이터 수집 시점에 굽혀 있다. `reward_config.json`을 바꿔도 **기존 100만 틱 데이터셋의
  리워드는 안 바뀌고 온폴리시 데이터만 바뀐다**(§4 참고).

### H2. 이동 결정 단위의 신호가 희귀한 점프에 묻힘
- **상태: 미검증 (정황 강함)**
- **근거**: Σr²의 90%가 0.12%의 틱에 몰려 있다. 네비 쉐이핑은 한 타일 접근에 최대 약 0.006인데, 결정당으로
  나누면 1e-4~1e-3 수준이고 Q std는 3.6~4.5다. Run 4 진단에서 막힌 틱의 top1-top2 margin(0.80)이 정상
  틱(1.45)보다 낮았고, 12틱 이상 막힌 구간의 100%가 같은 방향을 유지했다.
- **예상 증상**: PER과 IQN이 점프를 맞추는 데 용량을 쓴다. 이동은 Q로 구분되지 않고 BC가 대신 가르친다.
  벽을 향해 같은 방향을 고수한다.
- **입증 방법**:
  1. 새 로그 `q_value/action_margin`을 네비 쉐이핑의 결정당 기대 크기와 비교. margin이 쉐이핑 신호보다
     훨씬 크거나(노이즈 우세) 0 근처면 지지.
  2. 새 로그 `bc/accuracy`, `loss/bc_raw`: BC 정확도는 높은데 margin이 작다면 → 이동을 BC가 떠받치는 상태.
  3. 체크포인트 롤아웃에서 벽에 막힌 틱의 margin 분포를 정상 틱과 비교(Run 4 `diagnose_qvalues.py` 재사용).
  4. A/B: 점프 리워드 클리핑/정규화, 또는 `navPotentialEta` 상향 후 막힘 비율과 margin 변화.

### H4. 개인 네비 포텐셜이 몰려가기를 보상함
- **상태: 전제 확인됨, 수정 적용 (2026-09-15, Unity 빌드 반영, 미커밋)** — 효과는 미검증
- **근거 (코드 확인)**: `IndividualNavPotentialCalculator.NearestUnclaimedItemDistance`
  (`IndividualNavPotentialCalculator.cs:91-119`)
  - 빈손인 유닛마다 **독립적으로** 가장 가까운 아이템을 목표로 잡는다. 팀원과 목표가 겹치는지 보는 예약
    로직이 없다(휴리스틱은 `strategic.py` `_choose_target`의 `reservations`로 막음).
  - **아이템 타입이나 가치 필터가 없다**. 바닥에 있고, 저장소 밖이고, 상호작용 가능하면 버프/디버프 특수
    아이템도, 1개짜리 배터리도 15개짜리와 똑같은 목표다.
- **예상 증상**: 근처 유닛 여럿이 같은 아이템으로 몰린다. 가치 낮은 아이템을 우선한다. 사냥·호위·견제는
  Ψ 점프 말고는 보상이 없다. 사용자가 GUI에서 관찰한 "전략적 비효율"과 부합한다.
- **입증 방법**:
  1. 체크포인트 롤아웃과 휴리스틱 데이터에서 "같은 틱에 같은 최근접 아이템을 향하는 팀원 수" 분포 비교.
     `agent_states` 위치와 `graphic` 채널 8~12(아이템)로 오프라인 계산 가능하다. 격자 경로거리는 벽 채널로
     BFS 근사.
  2. 롤아웃에서 목표 아이템의 배터리 개수 분포, 특수 아이템을 향한 이동 비율 측정.
  3. A/B (C# 수정과 빌드 필요): 팀 단위 예약, 또는 아이템 가치 가중 네비 포텐셜.
- **수정 (`IndividualNavPotentialCalculator.cs`, `ComputePotentials`)**:
  - 목표는 Ψ가 가치를 매기는 **점수 배터리만**(`ScoreItemEffect`). 특수 아이템은 목표에서 빠지고, 들고 있어도 Φ=0.
  - Φ = (수량 ÷ 최대 수량) × (1 − tanh(거리/12)). 운반 중에도 같은 가중치를 곱해 픽업 순간 Φ가 튀지 않는 성질을 유지.
  - 팀 단위 탐욕 배정: (유닛, 배터리) 쌍을 가중 Φ 내림차순으로, 배터리 하나에 유닛 하나. 배정 못 받은 유닛은 Φ=0.
    동률은 유닛 번호, 칸 좌표 순으로 깨서 상태의 결정론적 함수로 유지(포텐셜 기반 쉐이핑 조건).
  - 성능: 배터리마다 저장소 거리를 따로 구하지 않고, 팀·아이템 종류마다 저장소 타일에서 퍼지는 거리장
    (`GridPathfinder.DistanceField`)을 틱당 한 번 계산.
  - 부작용: 팀원이 더 가까워져 배정이 바뀌면 그 유닛의 Φ가 자기 행동과 무관하게 떨어질 수 있다(상태 함수라 이론상
    정책 불변이지만 분산은 늘어난다).
  - **주의**: 정적 데이터셋의 리워드는 수집 당시의 옛 Φ로 계산돼 있다. 이 수정은 **새로 수집하는 온폴리시 데이터에만**
    반영된다. 데이터셋까지 맞추려면 새 빌드로 재수집해야 한다.

### H5. 벽 충돌 페널티의 부작용
- **상태: 전제 확인됨, 사망 대기 제외 수정 적용 (2026-09-15, 미커밋)** — Run 5 체크포인트 기준 모델이 받는 페널티의 38%가 사망 대기였음 (§3.6)
- **근거**: 틱당 평균 −0.00098로, 종료 제외 **부호 있는** 평균 리워드(−0.00005)의 약 20배다. 방향성 있는
  밀집 항 중 가장 크다. 정지 유닛-틱의 17.7%가 리스폰 텔레포트로 끝나는 구간, 즉 사망 후 대기다.
  `blocked_penalty_adjustment`는 텔레포트 틱만 빼고 그 앞의 정지 구간은 벌한다.
- **예상 증상**: 행동과 무관한 사망 대기에 벌이 붙는다. 교전이나 저장소 앞 몸싸움 같은 불가피한 막힘까지 벌받아
  경합을 회피한다.
- **입증 방법**:
  1. 새 로그 `onpolicy/self_vs_heuristic/candidate_blocked_penalty_per_tick`을
     `candidate_env_reward_per_tick`과 비교 — 페널티가 환경 리워드와 같은 크기이거나 더 크면 지지.
  2. 롤아웃에서 막힌 틱을 (a) 리스폰 대기 (b) 적 인접 (c) 순수 벽으로 분류하고 비율 측정.
  3. A/B (Python만 수정): 리스폰 대기 구간과 적 인접 구간을 제외한 페널티 vs 현행 vs 0.
- **수정 (`reward_shaping.blocked_penalty_adjustment`)**: 정지 구간이 끝나는 바로 다음 틱이 리스폰 텔레포트
  (이동 > 0.15, 에피소드 경계 제외)면 그 구간 전체를 사망 대기로 보고 벌하지 않는다. 관측에 생존 플래그가 없어서 이
  기준을 쓴다. 데이터셋 로드 시 다시 계산되므로 **정적 데이터셋에도 소급 적용**된다. 데이터셋 기준 틱당 페널티
  −0.00098 → −0.00081(17% 감소, 앞서 측정한 사망 대기 비중 17.7%와 일치).
  - 적 인접 막힘(측정상 0.4%)은 영향이 작아 제외하지 않았다. 페널티 크기는 실행 인자 `--blocked-penalty`로 조절.

### H6. 팀 브로드캐스트로 인한 크레딧 할당 실패
- **상태: 미검증**
- **근거**: Ψ 쉐이핑이 5명 전원에게 똑같이 들어가고 팀 합으로 학습된다. 개인별 반사실적 크레딧
  (제안서 §7)은 Phase 2로 미뤄져 있다. 누가 기여했는지는 QMIX 믹서가 추론해야 하는데, 오프라인 데이터의 행동
  정책이 휴리스틱이라 이 추론 근거가 약하다.
- **예상 증상**: 무임승차하거나 소극적인 유닛이 생긴다. 팀 내 유닛들의 Q가 비슷해진다.
- **입증 방법**:
  1. 롤아웃에서 유닛별 이동거리, 목표 근접 시간, 픽업/전달 횟수의 팀 내 분산 측정 → 일부 유닛만 일하는지.
  2. 같은 상태에서 유닛별 Q 행렬의 유닛 간 분산 측정.
  3. `mixer_clamp_pressure/*` 추이 확인 (믹서가 기여 분배에서 막히는지).

### H7. 흡수 경계 done 절단 때문에 Ψ/Φ의 빈틈이 그대로 드러남
- **상태: 특수 아이템 부분은 H4 수정으로 해소 (Φ 목표에서 제외). done 절단 자체는 미검증
- **근거**: done은 약 475결정마다 온다. 승패 ±1은 매치의 마지막 구간에만 전파되고, 그 전의 모든 행동은 Ψ/Φ로만
  배운다. Ψ에 없는 가치(특수 아이템 효과, 픽업 방해, 위치 선점)는 학습 신호가 0이다. 반대로 H4에서 확인했듯
  Φ는 특수 아이템을 목표에 포함하므로, **들고 가는 건 보상받지만 쓰는 가치는 0**이다.
- **예상 증상**: 특수 아이템을 무의미하게 운반한다. 장기 전략(견제, 선점)이 없다.
- **입증 방법**:
  1. 롤아웃에서 특수 아이템 픽업 빈도와, 픽업 후 실제 효과(버프 지속시간 동안의 이동·점수 변화) 측정.
  2. A/B: 실제 매치 종료에서만 done을 찍고 흡수 경계 절단을 끈 짧은 런 (γ 일관성 유지 필요).

### H8. 온폴리시 패배 데이터가 버퍼의 리워드 분포를 한쪽으로 끌어내림
- **상태: 확인됨** — 실제 상태 기준 Q가 페널티로 가득 찬 실제 리턴을 따라감 (셀프플레이 상관 0.94, §3.6)
  맞물린 데이터 구성 문제.
- **근거**: 후보 모델은 휴리스틱에게 전패다. 이 매치들은 종료 −5, Ψ≈−1로 포화, 벽 충돌 페널티를 가진 채 FIFO
  버퍼의 휴리스틱 데이터를 밀어낸다. 휴리스틱 데이터는 승패가 거의 반반이다.
- **예상 증상**: `q_value/mean`이 리셋과 무관하게 단조 감소하고 `q_value/std`는 증가 (Run 5에서 관측됨).
- **입증 방법**:
  1. 새 로그 `buffer_source_frac/*`와 `q_value/mean`의 시간축 비교, `batch_n_step_return`과
     `batch_td_error`의 출처별 비교.
  2. Run 4(온폴리시 없음)와 Run 5의 Q 궤적 비교 (H1-1과 같은 작업, **지금 가능**).
  3. A/B: 온폴리시 비율 0 vs 현행을 짧은 런으로 비교하거나, 온폴리시 데이터를 따로 저장해 샘플링 비율 고정.

### H9. 학습 중 생성된 트랜지션에 BC loss가 걸려 모델이 자기 행동을 모방함 (리워드 외 원인)
- **상태: 코드로 확인, 수정 적용 (2026-09-15, 미커밋)**
- **근거**: Run 5까지 BC loss(`cross_entropy(own_q_values, taken_action)`)는 배치의 출처와 상관없이 모든 샘플에
  걸렸다. 온폴리시 데이터(셀프플레이 전부, 휴리스틱 상대 경기)의 행동은 모델 자신의 greedy 행동이다. BC는 Q값을
  로짓으로 쓰므로, 그 행동의 Q를 다른 행동보다 **직접 끌어올린다**.
- **예상 증상**: TD는 벽 쪽 행동을 나쁘다고 학습하는데(셀프플레이 상태의 Q −10.4, 실제 리턴과 상관 0.94) BC가
  같은 행동을 반복하도록 당겨서 정책이 안 바뀐다. Run 5의 막힘 비율이 온폴리시 주입 후에도 휴리스틱 상대 49%,
  셀프플레이 94%로 남은 것과 부합한다.
- **수정**: 버퍼에 행 단위 `demo` 플래그(그 스트림의 팀을 휴리스틱이 조종했는지)를 추가하고, BC는 `demo`
  행에만 적용한다(`qmix_trainer.py` `bc_mask`). 모든 샘플이 시연 데이터면 이전과 똑같이 계산되고, 모델이 조종한
  샘플은 BC 기여가 0이다 (CPU 수치 테스트로 확인).
  - 시연으로 보는 것: 정적 데이터셋, **휴리스틱 상대 경기의 휴리스틱 쪽 스트림**, 온라인 1단계, 온라인 2단계의
    풀 에피소드 휴리스틱 상대 스트림, 병렬 learner의 부트스트랩 데이터.
  - 휴리스틱 쪽을 포함한 이유: 휴리스틱이 서툰 상대를 만났을 때의 행동은 휴리스틱끼리 데이터셋에 없는 분포다.
  - Unity 스모크 테스트에서 좌우 교대에 맞게 태그가 붙는 것과, `bc/active_frac`이 기대값(약 0.83)대로 나오는 것을
    확인했다.
- **입증 방법**: Run 6에서 `bc/model_action_agreement`(모델이 조종한 행에서 argmax가 실제 행동과 일치하는
  비율)와 온폴리시 막힘 비율(`onpolicy/self_vs_heuristic/candidate_blocked_unit_frac`)이 Run 5보다 떨어지는지
  확인.

  유닛이 서 있는 칸의 81.8%). 장애물은 채널 1(벽)뿐이다.

## 5. 온폴리시 주입 직후의 그래디언트 스파이크와 Q 계단 (Run 5 TB, 2026-09-15)

H8을 보강하는 관측. 리워드 설계보다는 데이터 주입 방식의 문제에 가깝다.

- **Q 계단**: 10k 주입 직후 `q_value/mean`이 급락하고 2k 스텝 안에 일부 회복한다. 예: 80k −0.76 → −3.86 →
  −1.52, 120k −2.21 → −4.98 → −1.73. 즉 `q_value/mean`은 PER 배치 평균이라, Q 하락의 일부는
  배치 구성이 쏠린 효과다.
- **그래디언트 스파이크**: 주입 직후 첫 로그 스텝의 `grad_norm/total_preclip`은 평균 4.33으로, 평상시(0.60)의
  7배다. Run 4에는 이 패턴이 없다. 크기도 커져서 130k~150k에서 11.8 / 11.2 / 15.1로 `grad_clip=10`을 넘었다.
  - 부위별(주입 직후 ÷ 평상시): graphic_encoder 19.8배, attention 8배, spr_head 5.9배, q_head 1.7배,
    dist_mixer 0.6배.
  - SPR loss도 튄다 (130k: 0.0015 → 0.19).
- **추정 기전**:
  - 새 전이가 역대 최대 우선순위로 들어가는데(`replay_buffer.py:110`), 이 최대값은 줄지 않는다(`:221`).
    → 주입 직후 배치를 새 데이터가 차지하고, 최대값이 커질수록 쏠림도 커진다.
  - 중요도 가중치는 IQN loss에만 곱해지고 SPR(×5)과 BC에는 곱해지지 않는다(`qmix_trainer.py:1059`).
    → IQN만 받는 q_head/믹서는 조용하고, SPR·BC를 받는 인코더가 충격을 받는다.
- **분리 못 한 것**: 셀프플레이와 휴리스틱 상대 경기는 같은 스텝에 같이 주입돼서 어느 쪽이 주범인지 모른다.
- **적용한 수정 (2026-09-15, 미커밋)**: 데이터셋은 고정하고, 온폴리시 데이터는 출처별 작은 FIFO 버퍼로 분리한 뒤
  배치를 버퍼별 고정 비율로 뽑는다(`QMIXConfig.batch_source_fracs`, `onpolicy_buffer_capacity`,
  `QMIXTrainer._sample_stream`).
  - **데이터셋 고정**: 이전에는 온폴리시 데이터가 데이터셋과 링 버퍼 하나를 같이 써서, 데이터셋에서 가장 먼저 수집된
    에피소드부터 순서대로 덮어썼다(Run 5에서 스트림당 약 41만 행, 데이터셋의 41% 소실). 이것도 후반 Q 하락에
    일조했을 것으로 본다. 이제 `buffer_a/b`는 로드 후 쓰이지 않는다.
  - **온폴리시 버퍼**: 출처(휴리스틱 상대, 셀프플레이)마다 스트림당 `--onpolicy-buffer-capacity`행(기본 262,144,

  - **배치 비율**: 수집 인자에서 계산 — 데이터셋 : 휴리스틱 상대 : 셀프플레이 = (1 − 두 비율) :
    `--onpolicy-self-vs-heuristic-frac` : `--onpolicy-self-play-frac`. 아직 n-step/SPR 윈도우를 못 채우는 버퍼의
    몫은 나머지에 비례 재분배.
  - **우선순위**: 버퍼마다 트리와 최대 우선순위가 따로라, 새 온폴리시 데이터가 최대 우선순위로 들어와도 그 출처 몫
    안에서만 쏠린다. 중요도 가중치는 버퍼 내부 편향만 보정하고(정규화 전 가중치를 합친 배치 전체의 최대값으로
    정규화), 출처 간 비율은 보정하지 않는다. 정규화 기준을 전체 최소 우선순위에서 배치 최대값으로 바꿨다
    (Dopamine/BBF 방식).
  - 검증: 버퍼·트레이너 CPU 테스트 14개(할당량, 재분배, 버퍼별 우선순위 갱신, 데이터셋 불변, FIFO 상한)와 Unity
    스모크 테스트(휴리스틱 상대 2경기가 전용 버퍼에만 들어가고 상한에서 오래된 행부터 밀려남, 데이터셋 버퍼 불변,
    배치 비율 0.708/0.292 = 24행 중 17/7) 통과.

## 8. 특수 아이템 리워드 (H10, 다음 실험 후보 — 2026-09-16)

Run 7 GUI 관찰에서 나온 제안: **DebuffSpeed는 승패에 미치는 영향이 배터리 한 개보다 크다.**
현재 리워드에서는 특수 아이템이 Φ 목표에서도 빠지고 Ψ 가치도 0이라 **관련 행동에 학습 신호가 전혀 없다**
(§6의 보류 항목).

### 시간 의존성이 배터리와 정반대다

Unity 확인 결과(`ItemObject`, `BuffItemEffect`, `LevelDirector.OnAbsorption`):

- 특수 아이템은 **창고에 놓여 있는 동안** 효과가 적용된다(`BuffItemEffect`가 대상 팀에 모디파이어 부여).
- **흡수 시점에 효과가 사라진다.** `ItemObject.ApplyEffectInternal`이 모든 퇴장 사유에서 모디파이어를 되돌리고,
  `BuffItemEffect`의 주석도 "흡수 포함 모든 퇴장에서 사라진다"고 명시한다.
- 배터리는 정반대다. 흡수가 점수를 **확정**한다(`ScoreItemEffect`: `case ItemExitReason.Absorbed: // 잠금`).

따라서 **특수 아이템의 가치는 흡수 직후 최대, 흡수 직전 최소**이고, 흡수 주기에 따라 선형에 가깝게
감소한다. 배터리에는 이런 시간 의존성이 없다. (정정 2026-09-16: 흡수 주기는 C# 기본값 120초가 아니라
`GameBalanceConfig.asset`의 **20초**다. `heuristic_findings_for_reward_20260916.md` §1, §4.5 참고.)

- 특수 아이템은 중립 타일에만 스폰한다(`LevelDirector.FilterAvailableSpawnPos`).
- 창고 타일 하나를 통째로 차지하고 병합되지 않으므로(`MaxItemAmount: 1`), **배터리 용량을 잡아먹는다** —
  `derived_obs.storage_free_capacity`가 이미 이 타일을 0으로 친다.

### 설계 스케치

```
Φ 가중치(특수) = 기본값(종류별) × (흡수까지 남은 시간 / 흡수 주기)
기본값: DebuffSpeed > 배터리 1개 > 그 외 특수
```

시간 비례 항이 "흡수 직전에 주워봐야 소용없다"를 자동으로 표현한다. 관측에는 `absorption_time_left`가
이미 팀 스칼라로 들어가 있으므로 모델이 타이밍 자체는 볼 수 있다.

### 왜 Run 8에 넣지 않는가

1. **귀속.** Run 8은 "없던 정보를 주면 측정된 세 현상이 고쳐지는가"를 묻고 판정 지표가 그에 맞춰져 있다.
   리워드를 같이 바꾸면 배터리·배달 지표가 두 이유로 움직여, Run 5~7에서 반복된 "개선했는데 원인 불명"이
   또 생긴다.
2. **비용.** 리워드는 데이터셋에 기록되므로 Unity 재빌드 + 전체 재수집이 필요하고, Run 7까지의 수치와
   직접 비교가 끊긴다. 관측 변경은 이미 구현돼 추가 비용이 없다.
3. **배터리 접근(상대의 51%)은 Run 8이 이미 겨냥한다.** 지금까지 모델은 바닥의 배터리와 주울 수 없는
   자기 창고의 배터리를 같은 채널로 봤다(`fetchable_battery` 채널이 이를 분리한다). Run 8에서 접근 속도가
   오르지 않으면 그때 리워드로 넘어가는 것이 순서다.
