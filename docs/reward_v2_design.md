# 리워드 v2 설계 — 유닛별 포텐셜, 휴리스틱으로 평가 (2026-09-17, Run 11에 쓰인 `FITTED_20260917B`)

기존 리워드(Unity 쪽 팀 Ψ + 개인 네비 Φ + 종료 ±1)는 V1–V6 시절 `docs/archive/reward_proposal.md`로 설계됐다. 그 뒤 V17–V19를
만들며 측정한 게임 역학(`heuristic_findings_for_reward_20260916.md`)과 여러 곳에서 어긋나고, Run 5–10 동안
땜질(Hunter Φ, 벽 막힘 페널티)만 쌓였다. 이 문서는 처음부터 다시 짠 설계와, **휴리스틱을 이용해 유닛 단위로
리워드를 평가하는 방법**을 정한다. 설계는 구현·적합을 거쳐 Run 11에 쓰였다(§6b 진행 기록). 코드와 다른 곳은
2026-09-19에 코드 기준으로 고쳤다.

## 1. 원칙

1. **종료 보상 + 포텐셜 기반 쉐이핑만 쓴다.** 고정 이벤트 보상(킬·데스·적재)은 쓰지 않는다. 모든 설계 의도는
   상태 함수 V(s)에 넣고, 보상은 `γ·V(s') − V(s)`로만 나온다. 루프 악용(왕복, 줍고 버리기)이 원리적으로 막힌다.
   (구현: 실제 보상은 종료 ±5와 확정 점수 변화 §2.1. 예외로 Run 11은 막힘 페널티 0.02/유닛-틱을 따로 더한다 —
   포텐셜 차가 아니므로 최적 정책을 바꾼다.)
2. **V는 "지금 상태에서 기대되는 최종 점수차"의 근사다.** 단위는 배터리 점수. 휴리스틱 실험의 측정값이 각 항의
   가중치 근거가 된다.
3. **유닛별로 분해한다.** 팀 가치 V_team(s) = C(s) + Σᵢ Uᵢ(s). 각 항은 그 가치를 만들거나 지키는 유닛에게 귀속하고,
   누구의 것도 아닌 항(창고 보유 C)만 5등분한다. QMIX는 팀 합만 쓴다 — 유닛별 분해는 `shaped_rewards()`로
   평가(§5 E1·E2)에서만 계산하고 버퍼에는 저장하지 않는다(§4).
4. **제로섬.** 팀 A의 보상은 ΔV_A − ΔV_B. 적 운반자를 죽이면 적의 운반 가치가 사라져 우리 쪽 보상이 된다 — 킬
   보상을 따로 두지 않아도 된다. 적 쪽 가치 변화는 그 적에게 배정된 우리 유닛(없으면 5등분)에 귀속한다.
5. **시간 가치.** 편성·위치 항(U4 진치기, U5 준비도)은 "아직 판에 남아 있는 배터리 가치의 비율" e(t)로 곱한다.
   필드가 비면 위치·편성의 가치는 0으로 수렴하고, 창고·운반 중인 배터리와 확정 점수만 남는다.
6. **γ는 학습기와 같게.** 쉐이핑 γ를 학습기 γ와 따로 두면 정책 불변성이 깨진다(H1). 쉐이핑을 Python에서
   계산하면 학습 시점의 γ를 그대로 쓸 수 있다(§3).
7. **관측으로 계산 가능해야 한다.** 그래야 저장된 데이터와 가상의 한 걸음(§5 E1)으로 오프라인 평가가 된다.

## 2. 포텐셜 구성

기호: aᵦ 배터리 점수, d 경로 거리(칸), v 유닛 속도(칸/초; Collector 4, Hunter·Carrier 6), τ 다음 흡수까지 남은 초.
V는 점수 단위이고 학습 보상으로 쓸 때 20점 = 1로 나눈다(`POINTS_PER_REWARD`). closeness(d) = 1 − tanh(d/L).
모든 확률형 항은 `exp(−hazard·시간)` 꼴이고, hazard는 **실제로 그 배터리를 없앨 수 있는 적 클래스**까지의 경로
거리로만 계산한다.

### 2.1 확정 점수는 V 밖의 실제 보상 (구현 중 변경)

**화면 점수에는 창고에 넣어둔 배터리가 이미 들어 있다.** `ScoreItemEffect`가 창고에 들어올 때 더하고, 나갈 때
(약탈·파괴) 빼고, 흡수될 때만 확정한다. 그래서:

- **확정 점수 = 화면 점수 − 자기 창고의 배터리.** 매 틱의 실제 보상은 `Δ(확정_own − 확정_enemy)`다(흡수 틱에만 0이 아님).
- 확정 점수를 V에 넣으면 γ<1 때문에 매 틱 `−(1−γ)·점수`가 붙는다. 측정: γ=0.997에서 틱당 0.07점의 상수 편향.
- 흡수 순간 창고 가치(τ→0이라 할인 없음)가 확정 점수로 그대로 옮겨간다. 측정: 창고 72.9 → 확정 73.
- (참고) 기존 Unity Ψ는 화면 점수(창고 포함)에 창고 보유가치를 **또 더했다** — 창고 배터리를 두 번 셌다.

### 2.1b 공통 항 (5등분)

| 항 | 정의 | 근거 |
|---|---|---|
| C 창고 보유 | Σ(그 팀 창고 배터리) aᵦ·k_store(b) | 흡수 순간 창고에 있는 것이 점수 (§2.2) |

k_store(b) = 본진(보호) 창고면 1, 외부 창고면 `exp(−λ_s·τ / max(d_thief, 0.5))`(λ_s = steal_hazard), d_thief = 그 창고를 털 수 있는
**적 Collector·Carrier** 중 가장 가까운 경로 거리. 적 Hunter는 창고를 못 턴다(§4.1).

### 2.2 개인 항 (유닛 i에 귀속)

| 항 | 대상 | 정의 | 근거 |
|---|---|---|---|
| U1 운반 | 배터리를 든 Collector·Carrier | aᵦ · k_carry(i) · λ(d_deliver) | §2.3 운반 중 사망 |
| U2 수거 | 빈손 Collector·Carrier, 팀 단위 배정 | aᵦ · k_carry(i) · λ(d_fetch + d_deliver(b)) | 줍는 순간 U1과 같은 값 → 줍기 자체엔 보상 0 |
| U3 추격 | Hunter, 팀 단위 배정(적 비Hunter 중) | β · 먹잇감 가치 · closeness(d; L=hunt_length) | Run 9 진동 원인 |
| U4 진치기 | 적 본진에 붙은 칸에 가장 가까운 Hunter 1기(팀당) | w_exit · e(t) · closeness(d_적출구; L=exit_length) | §3.1–3.2 출구 봉쇄 |
| U5 준비도 | 모든 유닛 | e(t) · (w_class[c] + w_travel · min(d_스폰/v, T_cap)) | §4.2 빈손 사망 비용 |
| U6 변신 이동 | 빈손 Collector, 팀 Hunter 수 < H* 일 때 배정 | e(t) · w_class[Hunter] · closeness(d_성소) | §3.3 변신 타이밍 — **구현 안 함** |

Hunter 한 기의 U3/U4 칸은 둘 중 큰 값이다. U2 대상은 특수 아이템을 든 유닛을 뺀다. 배정(U2, U3)은 팀 전체에서 값이
큰 쌍부터 하나씩 고르는 탐욕 배정이다.

- **λ(d) = 1 − ρ·tanh(d/L)**: 멀리 있는 배터리는 할인. d_deliver는 **그 짐을 받을 수 있는 창고**까지의 거리
  (용량 반영) — 가득 찬 스폰 창고 앞 대기가 U1에서 곧바로 손해로 보인다.
- **k_carry(i)** = `exp(−carry_hazard·(min(d, 60)/v) / max(d_threat, 0.5))`: Collector는 적 **Hunter**, Carrier는 적
  **Hunter·Collector**(Collector가 Carrier를 이김)까지의 거리 d_threat로 계산한 생존 확률, d는 U1이면 d_deliver,
  U2면 d_fetch + d_deliver(b).
- **U2의 약탈 몫**: 적 창고의 배터리는 `(1 − 적의 k_store)`만큼만 가치로 센다 — 적의 C가 도둑에게 내준다고 본
  몫이다. 흡수 직전처럼 더 이상 못 훔치면 0이 되고, 두 팀이 같은 배터리를 이중으로 세지 않는다.
- **U3 먹잇감 가치**: 적의 U1(운반, 빈손이면 0) + 적의 U5(준비도). 처치하면 적의 U1/U5가 사라져 제로섬 보상이
  되고, U3 자체의 하락(목표 소실)과 상쇄되지 않도록 β < 1로 **적 가치 쪽이 더 크게** 둔다(처치 순보상 (1−β)·먹잇감 가치).
- **U5**: 죽으면 스폰에서 Collector로 부활 → 클래스 가치 w_class와 스폰에서 온 이동 시간 가치(스폰까지의 경로 거리 ÷
  속도, 상한 T_cap)가 사라진다. 이것이
  "잃은 시간 × 지금의 점수 획득률"이라는 §4.2의 사망 비용이다. 회피를 강제할 만큼 크지 않게 w는 E3·E5로 맞춘다.
- **U6**: 역할 의도는 관측되지 않으므로, 팀 Hunter 수가 목표 H*보다 적을 때만 가장 가까운 빈손 Collector를 성소로
  배정한다. **H*를 박아넣는 것은 V17 편성을 가르치는 사전지식**이라 기본은 끄고 E5로 효과를 본다. → 구현하지 않았다
  (`reward_v2.py`에 없음). 변신 신호는 U5의 클래스 가치가 대신한다.
- **e(t)** = (바닥 + 운반 중 배터리) / 초기 총량(200), [0, 1]로 자름. 창고의 배터리는 뺀다 — 흡수가 모든 창고를 한 번에 비우므로,
  넣으면 흡수 틱에 모든 유닛의 준비도가 동시에 떨어진다.

### 2.3 종료

구현: 경기 마지막 행의 보상 = `±5`(승패, 무승부 0; 저장된 Unity 보상의 부호에서 복원) `− P(s_last)`(다음 포텐셜
0). 데이터에는 경기 종료 뒤 상태가 없어서 **마지막 틱의 확정 점수 변화는 0으로 버린다** — 마지막 흡수가 확정하는
점수는 ±5 결과로만 들어간다. (설계 초안은 `w_win·(±1) + Δ확정점수 − V(s)`였다.) 흡수 경계 done 절단(20초)에서는
쉐이핑이 `γ^k·P(s_end) − P(s_start)`로 텔레스코핑되고 P(s_end)를 그대로 부트스트랩한다(`terminal`인 행만 0) —
P(s_end)가 절단이 버리는 가치를 대신한다.

## 3. 계산 위치: Python

쉐이핑을 Unity가 아니라 Python에서 관측으로 계산한다(`train/reward_v2.py`; 벽 막힘 페널티와 같은 자리 —
데이터 로드 `offline_dataset.load_dataset_into`와 온폴리시 수집 `onpolicy_collect` 양쪽). **결정 기준은 처리량이다.** Unity 쉐이핑은 물리틱(50Hz)마다 돌고, 과거 네비
포텐셜 첫 버전이 Unity CPU/스텝을 3배로 늘린 적이 있다. Python은 전이 묶음을 벡터화해 한 번에 계산한다
(`train/reward_v2.py`, 단일 프로세스 ~2,500 관측/초 → 100만 전이 × 12프로세스 ~1–2분).

- **평가·반복이 빠르다.** 가중치를 바꿔도 Unity 재빌드·재수집이 없다. §5의 평가가 전부 오프라인으로 돈다.
- **γ를 학습기와 맞출 수 있다**(원칙 6). n-step/γ 어닐링도 반영 가능.
- **유닛별 보상을 데이터 포맷 변경 없이** 만든다(관측에서 재계산).
- Unity 쪽 보상은 경기 마지막 행의 승패 부호만 읽는다. 그래서 Unity 쉐이핑을 켠 채 수집한 기존 데이터도 재수집 없이
  쓴다(Run 11 데이터가 그렇다, P3). `--no-unity-shaping`으로 수집한 데이터는 `--reward v2|v2-fitted`로만 쓸 수 있다.

관측에 없는 것과 대응:
- **본진 4×4 영역**: 맵이 고정이라 상수로 둔다(스폰 좌표에서 계산).
- **특수 아이템 재생성 타이머, 속도 디버프 적용 여부**: v1에서는 무시(H10은 별도).
- 경로 거리: 벽이 고정이라 전쌍 최단거리 표를 팀별로(상대 본진은 못 지나감) 한 번 계산해 둔다(576×576, 8방향, 벽
  모서리 가로지르기 없음). 유닛의 연속 위치에서는 주변 4칸을 쌍선형 보간한다.

## 4. 유닛별 보상의 소비

- 버퍼에는 팀 단위 보상(`reward`)과 팀 포텐셜 P = (V_own − V_enemy)/20(`potential`)만 들어간다(QMIX).
  유닛별 값은 버퍼에 기록하지 않는다 — `shaped_rewards()`가 관측에서 다시 계산하며, 지금은 평가(E1·E2)만 쓴다.
- 귀속 규칙: 자기 dUᵢ + 양 팀 dC의 1/5, 적 유닛 j의 −dU_j는 j에 배정된 우리 Hunter에게(없으면 5등분).
- 나중에 개별 크레딧 알고리즘(VDN 개인 타깃, MAPPO 등)으로 바꾸면 그대로 쓴다.

## 5. 평가: 휴리스틱으로, 유닛 단위로

리워드를 학습으로 검증하면 한 번에 몇 시간이 들고 원인이 섞인다. 대신 **강도를 아는 휴리스틱**을 기준으로 삼는다.
계획은 모든 항목에서 **지금 리워드(Ψ+Φ)와 나란히** 재는 것이었다. 구현은 E3에서만 기존 Ψ와 화면 점수를 나란히
보여준다(`fit_reward_v2.py`); E1·E2(`evaluate_reward_v2.py`)는 v2만 잰다. E3–E5는 20/40/60초 대신 2–40초 시점을
쓴다(첫 60초가 경기를 결정하고 녹화는 64초에서 끊음). E5는 누적 쉐이핑이 아니라 그 시점의 X = 확정 점수차 + V_A − V_B다.

| # | 질문 | 방법 | 통과 기준 (최초 제안; 실제 결과는 §6b) |
|---|---|---|---|
| E1 | 한 걸음 단위로, 좋은 휴리스틱이 가는 방향을 쉐이핑이 가리키는가 | 데이터의 각 유닛-틱에서 8방향으로 한 걸음(클래스 속도) 옮긴 상태의 쉐이핑을 계산, 휴리스틱이 실제로 고른 방향의 순위. 역할별(수거·운반·추격·진치기·변신 이동·기타) | 수거·운반·추격에서 top-3 ≥ 70%, 무작위 기준(37.5%)과 지금 리워드보다 높음 |
| E2 | 사건마다 부호와 크기가 측정과 맞는가 | 유닛별 보상을 사건 전후로 집계: 줍기, 적재(안전/외부), 약탈, 운반자 처치, 출구 빈손 처치, 운반 중 사망, 빈손 사망(초반/60초 후), 변신 | 표(§2.2 근거)와 부호 일치, 60초 후 빈손 사망 ≈ 0 |
| E3 | 가치가 결과를 예측하는가 | 휴리스틱 경기 수백 판에서 V_A − V_B를 20/40/60초에 기록 → 최종 승패 AUC, 최종 점수차 상관 | 60초 AUC가 지금 Ψ보다 높음 |
| E4 | 강한 정책이 더 높은 가치를 쌓는가 | 알려진 매치업(V17 vs V1–16 94%, V18 vs V17 78%, V19 vs V18 72%)의 첫 60초 평균 V 차 | 부호가 전부 맞고 크기 순서가 승률 순서와 같음 |
| E5 | 전술 변형의 승률 순서를 재현하는가 | findings §3.1의 V17 변형들(Hunter 0/1/2/3기, 전원 진치기, 혼합, 회피 강제)로 `race_gauntlet` → 팀 쉐이핑 누적(60초) | 승률 순위와 순위 상관 ≥ 0.8 |
| E6 | 악용 가능한 루프가 없는가 | 합성 궤적: 왕복, 줍고 버리기, 먹잇감 옆 맴돌기, 자살 후 부활, 창고 앞 대기 | 누적 보상이 유계, 대기·맴돌기는 0 이하 |

E1, E2는 기존 데이터(mixv5)로 Unity 없이 된다. E6은 하네스를 만들지 않았다(포텐셜 쉐이핑이라 루프 누적은 원리상
유계; 줍기·흡수 연속성 등은 `tests/test_reward_v2.py`). E3–E5는 휴리스틱 경기가 필요하다(64초 근사로 경기당 ~1초,
18프로세스). 경기별 정책 id와 관측 스냅숏은 `race_gauntlet` 대신 `examples/record_value_matches.py`가 기록한다.

## 8. 열린 문제

- E1은 "다른 유닛은 그대로, 한 유닛만 한 걸음" 근사라 협동 효과(몰아주기, 호위)는 못 본다. E5가 그 공백을 메운다.
- 휴리스틱이 최적이 아니다. E1에서 휴리스틱과 어긋난다고 곧 리워드가 틀린 건 아니다 — 그래서 E3–E5의 결과
  기반 지표를 함께 본다.
- 초기 조건 민감성(§6.1) 때문에 E3–E5는 변형당 ~100경기가 필요하다.
- 특수 아이템(H10)은 v2 범위 밖.
