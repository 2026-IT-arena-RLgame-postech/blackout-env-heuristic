# BlackOut 강화학습 정책 rl18 (2026-11-10, 공식 v1.0.2 대회 형식)

밸런스 패치(헌터 팀당 2기) 이후 규칙에서 학습한 정책입니다. 공식 대회 형식인 **ONNX 팀 모드**(`model.onnx` + `meta.json`) 그대로 제출할 수 있습니다.
브랜치 `feat/balance-patch`, 이 릴리즈 태그(`rl18-2026-11-10`)의 커밋에서 빌드했습니다. 직전 릴리즈 `rl17-2026-11-09`를 대체합니다.

| 파일 | 내용 |
|---|---|
| `blackout_rl18_750_onnx.zip` | 대회 제출물 (`model.onnx` 21.4 MB + `meta.json` = `{"mode": "team"}`) |
| `SHA256SUMS` | 체크섬 |

- **입출력:** 입력 `vector [5, 96]`, `graphic [5, 11, 96, 96]`, 상태 `state_in [5, 1231]` → 출력 `action [5, 2]`, 상태 `state_out`.
- **추론 시간:** CPU 약 2 ms/스텝 (제한 100 ms). 구조는 rl15–rl17과 같습니다.
- **검사:** 대회 검사 스크립트(`examples/check_competition_submission.py`)와 공식 정책 이미지 안의 `check_submission.py`를 모두 통과했습니다.

## 0. rl17 대비 바뀐 점

**암살형 약점을 거의 막았습니다.** rl16 이후 찾은 익스플로이터 **X8_assassin**(B6 + "적 헌터가 8칸 안에 보이면 항상 쫓아가 교환")과 **X9_assassin_u6**(같은 행동을 처음 6초만)은 rl14–rl16을 +44 ~ +49로 이겼고, rl17 it900도 +37 / +29로 이겼습니다. rl18 it750 상대로는 +14 / +12, 암살형 쪽 승률 0.5대로 떨어졌습니다.
- 원인: RL 정책은 두 번째 헌터 교환(약 4초)에서 살아남은 헌터로 상대 출구를 압박해 이기는데, 암살형은 그 헌터를 잡습니다. 분기 롤아웃으로 보면 X8 상대 6초 시점 결과 분산의 97%가 운(교환 결과)이라, 학습 신호가 잡음에 묻힙니다.
- 그래서 rl18은 **반복당 데이터를 2배**로 늘리고, **크리틱을 대규모 데이터로 미리 다듬었습니다** (§3.5).
- 동시에 held-out OOD 성능은 지금까지 모델 중 가장 높습니다 (평균 +67.1, 최약 +56.8).

## 2. 모델 구조

파라미터는 5.81M이고, 공식 관측을 받아 팀 5유닛의 이동 방향을 한 번에 냅니다. 학습할 때와 추론할 때 같은 네트워크(`blackout_env/model/my_model.py`의 `MyModel`)를 씁니다.

### 2.1 관측 복원 (ONNX 그래프 안, `blackout_env/official/obs_mask.py`)

공식 관측 한 프레임에는 다음 정보가 없습니다:
- 상대 유닛의 클래스
- 배터리 양 (바닥, 운반 중, 저장소)

그래서 그래프 안에서 프레임마다 다음을 처리합니다.

- **맵 변환:** 96×96 id 맵을 4×4로 묶어 24×24 타일 맵(13채널)을 만듭니다.
- **벡터 변환:** vector에서 유닛 상태 `[10, 12]`와 팀 상태 `[4]`를 만듭니다. 흡수 시계는 경기 시계에서 계산합니다.
- **ONNX 상태(1231 floats)에 두 가지 추적기를 둡니다:**
  - **상대 클래스 추적:** 변신·사망·리스폰을 따라갑니다.
  - **저장소 양 추적 (`track_storage`):** 점수 변화, 도난, 입금 위치, 고정 채움 순서, 흡수를 사용합니다. 50 Hz로 7만 프레임을 돌려 칸별 오류가 0이었습니다.
- **마스크 모드 3:** 바닥과 운반 중 배터리 양만 "있음"(상수 1/3)으로 가립니다. 상대 클래스와 저장소 양은 추적값을 씁니다.
  - 정답 정보를 모두 보여 준 오라클 실험에서도 성능 차이가 없었습니다(§5). 그래서 이 가림은 병목이 아닙니다.

### 2.2 트렁크

- **파생 특징:**
  - 맵 채널: 유닛 점유, 저장소 남은 용량, 주울 수 있는 배터리
  - 유닛별: 주변 벽 특징
- **토큰 48개:**
  - 시야 토큰 36개 (CNN 맵 인코더, 6×6 격자)
  - 유닛 토큰 10개 + 팀 상태 토큰 1개 (벡터 인코더)
  - 학습용 CLS 토큰 1개
- **위치·정체성 정보:**
  - 토큰 타입 임베딩
  - 슬롯 임베딩 (같은 위치에 겹친 유닛도 구분)
  - 2D RoPE: 시야 토큰은 격자 칸, 유닛 토큰은 실제 위치를 씁니다.
- **어텐션:**
  - 4층, hidden 256
  - Grouped-query attention + Exclusive Self-Attention (자기 값 성분을 제거해 문맥 집계에 집중)
  - SwiGLU FFN, RMSNorm

### 2.3 정책 헤드

- 유닛마다 **방향 32개 + 정지 1개 = 33 로짓**을 내고, 선택한 방향 칸 안의 **각도 오프셋**(32)을 더합니다.
- 추론할 때는 argmax로 고르고, 결과를 연속 행동 `(dx, dy)`로 바꿉니다.
- 팀 B 시점은 좌우를 뒤집은 정규 좌표계로 처리합니다.

## 3. 학습 과정

### 3.1 시뮬레이터

- 공식 Unity 게임을 Numba로 다시 구현한 배치 시뮬레이터입니다 (`blackout_env/sim`).
- 공식 v1.0.2 규칙을 따릅니다:
  - 헌터는 팀당 2기
  - 벽 충돌은 대각 이동을 한 번에 처리 (`OFFICIAL_CLAMP`)
- 공식 리플레이를 재생하면 모든 스텝의 위치가 일치했습니다.
- 학습과 평가 모두 공식과 같은 **50 Hz**(결정 1회 = 1틱)로 진행합니다.
  - 처음에는 25 Hz로 평가했는데, 개선 폭이 실제보다 크게 나와서 50 Hz로 바꿨습니다.

### 3.2 단계별 계보

| 단계 | 내용 |
|---|---|
| 휴리스틱 | V34를 기반으로 CEM 튜닝한 **B3** → 카운터 C0 → 레이스 순서 이용 **B4** → 경비 보충 **B5** → CEM 묶음 **B6** (가장 강한 휴리스틱) |
| 증류 D1–D7 | 교사 B3의 행동을 학생에게 학습시켰습니다. 마스크 모드 3 관측, 공식 충돌 시뮬, 30k 스텝 → **D7** |
| PPO 리그 rl_bp1–5 | D7에서 시작, 25 Hz |
| rl_bp6–9 | **50 Hz로 전환**. 익스플로이터(X1–X5)를 상대 풀에 추가해 blockade 약점을 메움 |
| rl_bp10–12 | 학습 시드를 32비트 전체로 확장 (배터리 배치 암기 방지), 상대 풀 비중 조정 |
| **rl_bp13** | **`stop_exhausted`**: 배터리가 모두 사라져 점수가 더 바뀔 수 없으면 경기를 끝냄. 이전에는 학습 샘플의 71%가 승부가 이미 정해진 구간이었습니다 |
| **rl_bp14** | **HL-Gauss 분포형 크리틱**을 오프라인에서 미리 학습해 넣음 (§3.4) |
| rl_bp15 | rl14 it1200에서 시작. 현재 정책의 데이터로 크리틱을 갱신하고, rl13 it750과 rl14 it900을 상대 풀에 추가 → it1800 (직전 릴리즈) |
| rl_bp16 | rl15 it1800과 그 학습 중 크리틱(검증한 크리틱 중 가장 정확: 10초 R² 0.80)으로 시작. rl14 it1200, rl15 it1200·it1800을 상대 풀에 추가 → it1050 (직전 릴리즈) |
| rl_bp17 | rl16 it1050과 그 크리틱으로 시작. 암살형 익스플로이터 X8·X9(각 5.2%)와 rl16 it1050을 상대 풀에 추가. PFSP-hard 때문에 실제로는 경기의 약 34%가 X8·X9였습니다 → it900 (직전 릴리즈) |
| **rl_bp18** | rl17 it900에서 시작. 크리틱은 rl17 it900 크리틱을 630만 행으로 다시 다듬은 것(§3.5). **수집기 2개 + 크리틱 분리**로 반복당 데이터 2배(약 6.4만 결정), 처리량 1.8배. 상대 풀은 rl17과 같음. **iteration 750이 이번 릴리즈** |

### 3.3 PPO 설정 (`blackout_env/rl/ppo.py`, 실행 스크립트 `reports/bp/rl/ppo_bp1.sh`)

- **수집:**
  - 수집기마다 256경기를 동시에 돌리고, 한 번에 128결정씩 진행합니다.
  - 비동기 구성: 학습기와 수집기를 분리하고, 수집기는 CUDA graph를 씁니다.
  - **rl18부터 GPU 4장:** 학습기(GPU 0), 크리틱 업데이트(GPU 1, 정책 업데이트와 동시에 스레드로), 수집기 2개(GPU 2, GPU 3). 두 번째 수집기는 별도 프로세스입니다(시뮬이 GIL을 잡기 때문). 같은 행동 정책 가중치로 자기 게임을 돌리고 배치를 합칩니다 (`blackout_env/rl/actor2.py`, `critic_device` / `actor2_device`). 반복당 약 6.4만 결정, 반복당 약 21.6초.
  - decoupled PPO를 씁니다 (중요도 가중치 상한 2).
- **보상:** 경기가 끝날 때만 줍니다. `sign(lead) + 0.2·tanh(lead/30)`
- **하이퍼파라미터:**
  - lr 6e-6, clip 0.15, 시작 정책에 대한 KL β 0.015
  - GAE λ 0.975, epoch 2, minibatch 1024
- **상대 풀 (약 50개, 고정 비중):**
  - 이전 RL 체크포인트 (약 47%)
  - 핵심 휴리스틱 B3–B6, C0 (약 19%)
  - OOD 성향 (약 19%)
  - B6 파라미터 변주 (약 15%)
  - 익스플로이터 X1–X9 (rl17부터 X8·X9 추가)
  - PFSP-hard로, 지는 상대와 더 자주 붙습니다.
- **리그:**
  - 자기 스냅샷: 상대 풀을 승률 70% 이상 이기면 지금 정책을 스냅샷으로 추가합니다. 최대 4개.
  - 상대별 advantage 중심화.
- **익스플로이터 루프:** RL 단계가 끝날 때마다 최신 정책을 이기는 휴리스틱을 찾아 다음 풀에 넣었습니다 (`blackout_env/train/distill/exploit_bp.py`).
  - 5라운드(대 rl15)에서는 후보 25개가 모두 졌습니다. 가장 강한 후보도 −39점이었습니다.
  - 6라운드(대 rl16)에서 완전히 새 성향을 탐색해 암살형 X8·X9를 찾았습니다 (`blackout_env/heuristics/exploit6.py`의 `StrategicX6`).

### 3.4 크리틱 (rl14부터)

분기 롤아웃으로 크리틱을 진단했습니다 (`examples/value_branch_diag.py`). 같은 상태에서 서로 다른 난수로 여러 번 이어서 플레이해 실제 기대값을 구하고, 크리틱 예측과 비교하는 방식입니다.

- **결과:**
  - 결과 분산 중 운으로 정해지는 몫은 10–35%뿐입니다.
  - 그런데 기존 크리틱은 10초 시점 R²가 0.3–0.55로, 초반 예측이 약했습니다.
- **해결:** 결과를 회귀로 맞히는 대신 **HL-Gauss**(101구간, ±1.4)를 썼습니다.
  - 약 2.8만 경기에서 상태를 고르게 뽑아, 최종 결과(Monte Carlo 목표)로 오프라인 학습했습니다 (`examples/critic_bench.py`).
  - R²: 6초 0.07 → 0.41, 10초 0.56 → 0.67.
  - 2M행 이상 학습하면 과적합이 생겨서, 그 직전에 저장했습니다.
- PPO는 이 크리틱을 `critic_init`으로 받아 학습을 이어 갑니다 (`critic_head=hlgauss`, 비동기 지원).

### 3.5 rl18의 크리틱 다듬기

- **진단:** X8 상대 분기 롤아웃에서 결과 분산 중 운의 몫이 3초 79%, 6초 97%였습니다. rl17 it900 크리틱은 3초 시점에 +0.75 낙관 편향이 있었습니다.
- **소규모 시도(실패):** X8·X9 비중 60%로 90만 행을 모아 다듬었더니, 50만 행 이후 과적합으로 RL 상대 정확도가 떨어졌습니다.
- **대규모 데이터:** rl17 it900 정책으로 GPU 2장에서 630만 행을 모았습니다 (X8·X9 각 20%, 나머지 풀 60%). 200만 행만 학습한 크리틱이 가장 좋았습니다. 800만 행은 과적합이었습니다.
  - X8 6초 −1.84 → +1.46, X9 6초 −0.13 → +0.39, rl15 6초 −0.37 → +0.27, rl15 10초 +0.47 → +0.69 (분기 롤아웃 기준 지표).
  - 휴리스틱 상대 6초 지표는 나빠졌지만, 거의 확정적으로 이기는 판이라 원래 판단 근거가 약한 지표입니다.

## 4. 평가 방법

- **시뮬 짝 비교:** 64경기 (32시드 × 진영 2개).
- **held-out OOD (`--opponent oodho`):** 학습 풀에 한 번도 넣지 않은 성향 10종입니다.
  - 경제형 3종, 템포형 3종, 헌터형 2종, 잡음형 1종, 레거시 1종.
  - 경기가 보통 40초 안에 끝나서, 전략 전환은 8–15초에 일어나게 했습니다.
- **익스플로이터 탐색:** 25개 후보를 각각 48경기씩 붙였습니다.
- **공식 실행기:** 공식 Docker 실행기에서 ONNX끼리 16경기씩 겨뤘습니다.

## 5. 시도했지만 채택하지 않은 것

| 시도 | 결과 |
|---|---|
| KDA 시간 메모리 (순환 PPO) | 메모리는 실제로 쓰지만, 상태 없는 모델보다 낫지 않았습니다. ONNX 상태가 4 MB로 커지는 문제도 있었습니다 |
| 오라클 (배터리 양을 모두 보여 줌) | it300에서 −4.8±8.1로 이득이 없었습니다. 정보 부족은 병목이 아닙니다 |
| 오프닝만 학습하는 GRPO | 120 iteration까지 개선이 없었습니다 |
| 상대 조건부 교사 증류 | 오프닝이 무너졌습니다 |
| 크리틱 앵커링 (오프라인 크리틱 쪽으로 당김) | held-out OOD +46.7로, 기본 설정 +57.6보다 나빴습니다 |
| 상대 임베딩 크리틱 | 효과가 없었습니다. 상대별 advantage 중심화가 이미 상대별 편향을 상당 부분 흡수하고 있었습니다 |
